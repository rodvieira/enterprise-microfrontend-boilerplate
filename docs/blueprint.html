/ 01

Product overview

The problem

Every existing micro-frontend starter in the ecosystem is either a full framework you have to adopt wholesale (Piral), a mature-but-dated router with no real domain example (single-spa), or a set of official generators locked inside a specific monorepo tool's ecosystem (Nx) — with toy demos (shop, cart, characters) that prove the mechanics but never the operational concerns real teams hit: shared auth, dependency drift, security boundaries, or what a second team building a second remote actually needs.

The product

A monorepo boilerplate that ships two working example micro-frontends (a dashboard and an admin panel) composed inside a shell, talking to each other through a typed event bus, sharing a design system and an authentication contract, with guard rails in CI that catch the two bugs that actually break micro-frontend architectures in production: dependency version drift and import boundary violations.

Explicit non-goals

  • Not a full framework (no proprietary vocabulary, no hosted cloud service).
  • Not locked to one monorepo tool's ecosystem — works standalone or split across repos.
  • Does not implement real authentication — ships the contract, not the login flow (see §8).
  • Does not chase Webpack-1.0-era browser support — targets evergreen browsers only.
/ 02

Key decisions and why

Every decision below is final, reached through explicit research during planning — not assumed. Each links to evidence gathered at decision time.

01

Name: enterprise-microfrontend-boilerplate

"microfrontend-starter" (the generic phrase) already has 5+ established competitors, one with 10.3k stars — a new repo cannot rank against that. "enterprise" + microfrontend had no strong OSS competitor at research time, and matches the author's real production experience (corporate Design System + Micro-Frontends at scale).

02

Bundler: Rspack, not Vite

Module Federation 2.0's flagship features (Manifest, Federation Runtime, Runtime Plugin System) have confirmed official support in Webpack and Rspack. Rspack itself was built by ByteDance specifically because Vite's esbuild/Rollup pipeline could not handle their Module Federation setup at scale. Production adoption: ByteDance/TikTok, Microsoft, Amazon, Discord, Mews (3min → 10s startup).

03

Module Federation 2.0 as the federation layer

The modern standard as of 2026 — dynamic TypeScript type sharing, manifest-based dynamic host discovery, unified runtime across bundlers. Rejected Qiankun (narrower international reach) and single-spa (pre-MF architecture, SystemJS-based, framework-less root config is a dated constraint).

04

React 19 + TypeScript strict + Tailwind CSS

Consistency with the rest of the author's portfolio. Tailwind has official Rspack support (PostCSS-based, plus a dedicated @rsbuild/plugin-tailwindcss that reads Rspack's module graph for minimal CSS output).

05

pnpm workspaces + Turborepo for the monorepo

Consistent with the author's other projects. Deliberately not Nx — Nx's generators are the strongest in the ecosystem, but require adopting Nx as the permanent monorepo tool. Turborepo generators (Plop-based) achieve the same scaffolding goal without that lock-in.

06

exposed/ vs internal/ as the contract boundary

Module Federation itself prescribes no folder structure — this convention is ours. Only code under src/exposed/ is listed in a remote's federation.config.ts exposes map and is importable from outside. Everything in src/internal/ is physically unreachable through federation.

07

Dual-repo readiness: monorepo convenience, separate-repo discipline

A separate repository enforces the exposed/internal boundary for free — there's no relative import path to another repository. A monorepo does not enforce this automatically. Solution: never use relative imports across apps, even in the monorepo, enforced by dependency-cruiser in CI, so migrating a remote out to its own repository later breaks nothing.

08

Generator built after two real remotes exist, not before

Building pnpm turbo gen remote before having two working remotes risks encoding the wrong abstraction. The dashboard and admin remotes are built by hand first; the generator is extracted from what both actually have in common. Documented as its own build-order decision (§15).

09

Authentication: contract and stub, not a real implementation

Every enterprise adopting this already has an identity provider (Okta, Entra ID, Auth0, Keycloak). Shipping a real login flow means shipping code that gets ripped out on adoption. Instead: a stable useAuth() / <ProtectedRoute> contract backed by an in-memory stub, plus a documented integration path. See §8 for the full reasoning, including the 2026 BFF security consensus this deliberately does not implement.

10

Two remotes, chosen to prove cross-remote communication, not just federation loading

Dashboard (analytics/overview) and Admin (users/permissions) were chosen because they mirror the most common real enterprise micro-frontend adoption pattern — internal backoffice split by team ownership — and because a role change in Admin updating a live KPI in Dashboard via the shared event bus proves the architecture end-to-end, not just that two apps can be loaded side by side.

Architecture

┌──────────────────────────────────────────────────────────────┐
│                          apps/shell                          │
│  React host · reads federation/manifest.ts per environment   │
└───────────────┬──────────────────────────┬───────────────────┘
                │  loads via                │  loads via
                ▼                            ▼
┌────────────────────────┐   ┌────────────────────────┐
│    apps/dashboard       │   │      apps/admin         │
│  exposes: ./App         │   │  exposes: ./App         │
└───────────┬──────────────┘   └───────────┬──────────────┘
           │                                │
           └──────────┬─────────────────────┘
                     ▼
   packages/event-bus  packages/auth  packages/ui  packages/shared-types
   (all singleton-shared across shell + every remote)

Non-negotiable principles

  • Module Federation prescribes no folder structure. Host/Remote, Manifest, and shared-deps are the only official concepts — everything else here is convention we designed and documented.
  • Shell never imports remote internals. Only federation/loadRemote.ts touches remote code, and only through the federation boundary.
  • Singletons are enforced, not assumed. React, ReactDOM, packages/auth, and packages/event-bus must resolve to one shared instance — checked in CI, not just configured and hoped for.
  • No relative imports across apps. Even inside the monorepo. This is what makes moving a remote to its own repository later a non-event.
/ 05

Integration structure (exposed/internal)

Inside the shell — manifest-driven remote registry

apps/shell/src/ ├── federation/ │ ├── manifest.ts # reads the right JSON for the current env │ ├── remotes.dev.json # localhost:port per remote │ ├── remotes.staging.json │ ├── remotes.production.json │ ├── loadRemote.ts # wraps packages/federation-utils │ └── types.ts # RemoteModule contract ├── routes/ │ └── remote-routes.tsx # route path → remote mapping └── App.tsx

Switching environments is switching a JSON file, not recompiling the shell. Adding a remote touches the manifest, never the shell's own code.

Inside every remote — the contract for anyone integrating

apps/<remote-name>/ # or a fully separate repository, same layout ├── src/ │ ├── exposed/ # ★ only this is federation-importable │ │ ├── App.tsx │ │ └── routes.ts │ ├── internal/ # business logic, never exposed │ └── bootstrap.tsx # standalone entry — runs remote alone ├── federation.config.ts # what it exposes + what it shares └── remote.manifest.json # name, version, routes, owning team

The real boundary is enforced by repository topology, not convention alone. A separate repository has no ../ to another team's internal code — the boundary is physical. A monorepo doesn't get that for free: dependency-cruiser runs in CI to catch any relative import crossing an app boundary, so the rule holds identically whether a remote lives in this monorepo or gets split out to its own repository later.

Dual-mode generator

pnpm turbo gen remote ships two output modes:

  • Monorepo mode — creates apps/<name>, workspace-linked to packages/*.
  • Standalone mode — generates a fully independent project, consuming packages/* as published dependencies (via GitHub Packages) instead of workspace links. Changesets is the publishing engine, not just a changelog tool.
/ 06

Remote examples: dashboard + admin

apps/dashboard — Analytics/Overview

  • KPI cards (active users, usage trend) — proves async data fetching inside an isolated remote.
  • Activity chart over time — proves a third-party chart library works isolated inside federation without leaking CSS/JS into the shell.
  • Recent activity feed.

apps/admin — Users & Permissions

  • User table with pagination/sorting — proves a heavy shared data component (packages/ui) works across remotes.
  • Invite/edit modal — proves a form pattern plus a protected route (<ProtectedRoute> from packages/auth).
  • Role change action.

The detail that makes the demo worth watching: when Admin changes a user's role, Dashboard's "active users" KPI updates live — no reload, no direct coupling between the two remotes. The update travels through packages/event-bus. This is the proof that cross-remote communication works in practice, not just in the architecture diagram — and it's the moment the README demo GIF is built around.

/ 08

Auth/SSO strategy

No real login is implemented. Every enterprise adopting this boilerplate already runs an identity provider (Okta, Entra ID, Auth0, Keycloak). Shipping a real auth flow means shipping code that gets ripped out during adoption. What actually helps is the socket, not the plug.

What ships working (no server required)

// packages/auth — contract, stub implementation
export function useAuth() {
  return { user, isAuthenticated, login, logout }; // in-memory fake user today
}

export function ProtectedRoute({ children }) { /* gate on isAuthenticated */ }

Remotes consume the contract, never the implementation behind it. Swapping the stub for a real provider later touches nothing inside dashboard or admin.

What ships as documentation, not code

  • docs/how-to-connect-sso.md — where to swap the stub. Any OIDC-compliant provider (which covers the overwhelming majority of enterprise IdPs) enters through the same door, no per-provider code.
  • .env.example pre-named: AUTH_ISSUER_URL, AUTH_CLIENT_ID, AUTH_REDIRECT_URI.
  • A checklist of what to request from the company's identity team before wiring a real provider.

Security note, registered honestly

The 2026 consensus for SPA security is the Backend-For-Frontend (BFF) pattern — tokens never touch the browser, session lives in an HttpOnly cookie. Because this boilerplate is frontend-only by deliberate decision, BFF is documented as the recommended upgrade path (naturally connecting to a future Node.js-based project), not implemented here. This is a stated trade-off, not an oversight.

Guard rail extension: packages/auth must resolve to a single shared instance across shell and remotes — the same CI check that guards React/ReactDOM singleton drift now also covers "two divergent auth contexts."

/ 09

Security & CVE strategy

Category A — known CVEs in dependencies

LayerToolRole
Every PRpnpm audit --audit-level=highBaseline, free, built-in
Automated PRsDependabot or RenovateOpens a PR when a fix is available; Renovate is more configurable for monorepos
Local, pre-pushOWASP CVE Lite CLIRuns fully offline, suggests the exact fix command, catches pnpm workspace-level drift a root-only scan misses

Category B — malicious packages (supply chain, not CVE)

A different threat model: a package compromised on purpose (typosquatting, malicious install script) has no CVE because it isn't a documented flaw — it's an active attack. Socket analyzes what a package actually does (unusual network access, dynamic code execution) before it lands in the lockfile.

Category C — the risk unique to micro-frontends

The shell loads and executes remote code from a URL at runtime. If that origin is compromised, it's arbitrary code running inside the shell's own origin — a real supply-chain risk this category of architecture carries that none of the researched competitors document.

  • CSP (script-src) allow-listing only known remote origins.
  • Runtime origin allow-list — the shell refuses to load a remote from any URL outside the configured list, even if the manifest is tampered with.
  • HTTPS enforced outside local dev, validated by a script that fails the build on an http:// remote URL.
  • Manifest integrity hashing for remote pinning — flagged for technical validation during implementation, not asserted as already solved.

CI/CD

name: ci
on: [push, pull_request]
jobs:
  build-and-test:
    steps:
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo build      # each app isolated + shell composed
      - run: pnpm turbo test
      - run: pnpm check:boundaries  # dependency-cruiser
      - run: pnpm check:shared-deps # singleton drift guard
      - run: pnpm audit --audit-level=high

  e2e:
    needs: build-and-test
    steps:
      - run: pnpm exec playwright test  # shell + dashboard + admin composed
/ 14

Deployment

Each app deploys independently — the entire point of the architecture. Shell and both remotes on Vercel or any static host, each with its own build and its own deploy cadence. Manifest per environment means production simply points at the deployed remote URLs; nothing about the shell's own code changes between environments.

Definition of done

◆ Architecture

  • Shell composes dashboard and admin via manifest, no hardcoded remote URLs
  • exposed/ vs internal/ boundary enforced by dependency-cruiser in CI
  • React, ReactDOM, auth, event-bus verified singleton across shell + remotes
  • Cross-remote event (role change → KPI update) works end-to-end
  • Generator produces both monorepo-mode and standalone-mode output

◆ Security

  • pnpm audit, Dependabot/Renovate, Socket all wired into CI
  • CSP restricts remote script-src to known origins
  • Runtime origin allow-list rejects unknown remote URLs
  • HTTPS enforced outside local dev

◆ Portfolio

  • README opens with the cross-remote demo GIF and live URLs
  • CONTRIBUTING.md, CODE_OF_CONDUCT.md, issue/PR templates in place
  • ADRs committed for every decision in §2
  • Repo pinned, one technical post published
