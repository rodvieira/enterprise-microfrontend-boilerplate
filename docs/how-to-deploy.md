# How to deploy

Every app in this repository (`apps/shell`, `apps/dashboard`,
`apps/admin`, or any remote generated by `pnpm turbo gen remote`) builds
to static assets — no server-side rendering, no runtime backend of its
own. `output.publicPath: 'auto'` (every `rspack.config.ts`) means the
build makes no assumption about which domain it's served from. This
project has never committed to one specific static host, and this guide
doesn't either — the mechanism below works on any of them.

## Building an app for deployment

```bash
pnpm --filter @enterprise-mfe/dashboard run build   # → apps/dashboard/dist/
pnpm --filter @enterprise-mfe/admin run build        # → apps/admin/dist/
```

Each app's `dist/` is a complete, independent static site: upload it to
any static host (object storage + CDN, a static-site platform, a plain
web server) and it works. Per
[ADR-0007](decisions/0007-monorepo-and-standalone-parity.md), a remote is
deployable on its own — it needs nothing else from this repository at
runtime.

## The shell: one build per environment, via `FEDERATION_ENV`

The shell is the one app whose build output depends on which environment
it's built for:

```bash
FEDERATION_ENV=production pnpm --filter @enterprise-mfe/shell run build
FEDERATION_ENV=staging pnpm --filter @enterprise-mfe/shell run build
FEDERATION_ENV=dev pnpm --filter @enterprise-mfe/shell run build   # or omit — dev is the default
```

At build time, `apps/shell/rspack.config.ts` resolves `FEDERATION_ENV` to
one of three committed registry files
(`apps/shell/src/internal/federation/remotes.<env>.json`) and copies it
into the build output as `dist/remotes.json`
([ADR-0012](decisions/0012-runtime-registry-fetch.md)). At runtime, the
shell fetches `/remotes.json` once, on startup, and that file — not any
value compiled into the JavaScript bundle — is what tells it which
remotes to compose and which origins it's allowed to load code from.
**One build genuinely serves each environment**: deploying "to
production" means deploying the artifact built with
`FEDERATION_ENV=production`, nothing more environment-specific than that.

## Pointing the shell at a real deployed remote

Once `apps/dashboard` (or any remote) has a real, reachable URL, add an
entry to the registry file for the environment you're deploying to:

```jsonc
// apps/shell/src/internal/federation/remotes.production.json
{
  "environment": "production",
  "allowedOrigins": ["https://dashboard.your-domain.example"],
  "remotes": [
    {
      "name": "dashboard",
      "entry": "https://dashboard.your-domain.example/mf-manifest.json",
      "routePath": "/dashboard",
      "label": "Dashboard"
    }
  ]
}
```

`entry` points at the remote's own `mf-manifest.json` — Module
Federation's manifest, emitted alongside `remoteEntry.js` by every app's
build. `allowedOrigins` must include that URL's origin, or the shell
refuses to load it — both at the application level
(`origin-guard.ts`) and, since sprint 8, at the browser level (the
shell's own Content-Security-Policy, derived from this exact same list —
see `docs/architecture.md`'s "Remote loading" section). Then rebuild the
shell with `FEDERATION_ENV=production` so the new registry entry is
picked up.

**This repository's own `remotes.staging.json` and
`remotes.production.json` currently ship with empty `remotes` arrays.**
Building the shell for either environment today produces a working host
that composes nothing — correct, not broken, since neither environment
has a real deployed remote to point at yet. That's a maintainer's own,
separate action: deploy a remote for real, then add its entry here.

## What this guide is not

Not a specific host's dashboard walkthrough — Vercel, Netlify, GitHub
Pages, S3+CloudFront, and plain nginx are all equally valid choices for
static assets with no server-side requirement, and none of them changes
anything described above. Not an automated CI/CD deploy pipeline — this
repository has none yet, and adding one is a decision for whoever actually
runs a specific host, not a default this boilerplate should assume for
every adopter.
